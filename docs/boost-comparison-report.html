Comparison report

tsaver vs. JFrog Boost

A head-to-head check against JFrog Boost, the tool tsaver was originally inspired by. This includes a real bug the comparison surfaced in tsaver's pytest filter — found, fixed, and verified, not glossed over.

Boost's internals are closed-source (compiled Go binary, no public source repo) — this comparison is built from Boost's own published documentation and README, plus direct, reproducible runs of tsaver.

The headline result

Same input, same tool category (pytest), compared directly.

Boost's own README publishes a real before/after pytest example: 25 raw lines → 11 filtered lines, "same failure, same traceback, same summary." Run through tsaver's pytest filter before this comparison, that exact input produced 0% reduction — a real bug. Fixed during this comparison, tsaver now produces 25 → 12 lines on the identical input, and a line-by-line diff against Boost's own published output shows the two are identical except for one extra informational line tsaver adds on purpose.

What tsaver originally did with it — a real bug

Before this comparison, running that exact input through tsaver run -- pytest produced:

tsaver stats
  lines                   25 -> 25  (0.0% reduction)
  bytes                   1366 -> 1366  (0.0% reduction)
  words (approx. tokens)  91 -> 91  (0.0% reduction)
Root cause: tsaver's pytest filter looked for a bare line of dots (/^[.\s]*$/) to recognize passing-test progress output. Real pytest's default format prefixes each progress line with the file path and suffixes it with a percentage — tests/test_auth.py .............. [ 14%] — which never matches a dots-only pattern. Every progress line, and the entire startup banner, fell through to "keep as-is."

The fix

Three changes to src/filters/pytest.ts, in order of how much they contributed:

  1. Progress-line matching now recognizes the real pytest format (file path + status characters + optional percentage), not just bare dots.
  2. Startup banner dropping — the "test session starts" line, platform, rootdir, configfile, plugins, and collected N items lines are now dropped entirely, matching Boost's documented behavior ("drops: banner, plugins, progress dots").
  3. Decoration stripping on kept header/summary lines — === FAILURES === becomes FAILURES, matching the padding-free style of Boost's published output — plus suppressing blank lines left orphaned by a drop, without touching genuine blank lines that follow kept content.

  bytes                   1366 -> 395  (71.1% reduction)

Feature-by-feature

Based on Boost's published README and documentation (its filtering engine is a closed-source compiled binary, so internal thresholds/algorithms beyond what's documented can't be independently verified).

Custom per-tool filters Yes Yes Both use TOML files. Both offer a "gaps" command (boost filters gaps / tsaver filters gaps) that ranks noisy commands still falling through unfiltered.

File optimization (PDF/notebook/image) Yes Yes Both convert PDFs/notebooks to text/Markdown and resize images. Boost claims "2–3× fewer tokens" typical; tsaver measured a real 2 MB PDF at 99.9% byte reduction in the token savings report (see that report for why the token-count metric specifically doesn't apply well to this case).
Code graph / repo-wide symbol index Early access Regex heuristic Boost's BoostGraph claims real exploration speedups but is early access with no public algorithm detail. tsaver's graph build/query is openly a regex-pattern index, not an AST — documented as approximate by design, not a hidden limitation.
Reversible output (retrieve originals) Yes Yes boost retrieve <id> / tsaver retrieve <id> — same concept, nothing is ever discarded on either side.
Adaptive filter disabling Yes No Boost disables a filter locally after it's retrieved repeatedly (configurable threshold, default 3). tsaver has no equivalent — a real gap worth considering as a follow-up.
Local savings dashboard Yes Yes Both show aggregate savings and a "find opportunities"/filters gaps view. tsaver's dashboard additionally breaks out an approx.-tokens-saved tile and per-row column.

Editor/agent hook integration Yes Claude Code only Boost claims hooks for Claude Code, Cursor, Codex CLI, Copilot, OpenCode. tsaver only ships a verified Claude Code hook (Bash + Read tools) — other agents' hook formats weren't built against because they couldn't be verified in this environment.
Install method Signed binary release Git clone + npm link Boost ships signed platform binaries via install.sh/install.ps1. tsaver is source-only right now — see the troubleshooting section for known install friction on restrictive networks.

What this comparison actually establishes

  • On the one fully-specified, reproducible example Boost publishes, tsaver's output is now functionally identical — same failure, same traceback, same assertion, same summary, one extra line of deliberate tsaver-specific detail.
  • This required a real fix, not just a claim. The gap was found by actually running the comparison, not assumed away — tsaver's pytest filter had a genuine bug against real-world pytest output format before this report was written.
  • Boost has real, documented capabilities tsaver doesn't have: adaptive filter auto-disabling, verified multi-agent hook support beyond Claude Code, and OTel/PR integrations (the last two are deliberate scope decisions for tsaver, not oversights).
  • Boost's own internals can't be fully verified — it's a closed-source compiled binary with no public source repository, so claims about MCP compaction rules, BoostGraph's algorithm, and exact filter thresholds for tools other than pytest rest on documentation only, not independently reproducible code.

Methodology

  1. Boost's GitHub repository (jfrog/boost) was cloned directly to inspect for source code; it contains only install scripts, a GitHub Action wrapper, and release metadata — the actual filtering engine is a compiled Go binary not published in that repository.
  2. Boost's README.md and its linked documentation pages were read in full for every claim quoted or compared against in this report.
  3. The pytest example used in the deep-dive section is copied verbatim, character-for-character, from Boost's own published README (the "Without Boost" block), run as a real script that reproduces that exact output, then piped through tsaver run -- pytest.
  4. The "after" comparison is a literal diff between Boost's own published "With Boost" block and tsaver's actual stdout from that run — not a visual eyeball comparison.
  5. The pytest filter bug was found, fixed, and re-verified within this same session; the before-fix 0%-reduction result shown above was independently reproduced before any code change, and the after-fix result was reproduced again after.
