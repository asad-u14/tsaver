What each scenario actually was

1. Noisy test run (./noisy-tests.sh)

A real executable script producing 80 PASS lines across 10 modules plus one genuine FAILED assertion and a summary line — the shape of a real test suite. Run once raw, once through tsaver run --stats.

tsaver stats
  lines                   83 -> 9  (89.2% reduction)
  bytes                   3593 -> 424  (88.2% reduction)
  words (approx. tokens)  261 -> 40  (84.7% reduction)

75 near-identical PASS lines collapsed into one (×75) line. The FAILED line, its assertion detail, and the summary all survived untouched.

2. Noisy build (./noisy-build.sh)

A real script simulating a webpack-style build: 120 "building module N/120" lines plus a real warning and a success line.

tsaver stats
  lines                   123 -> 8  (93.5% reduction)
  bytes                   4682 -> 303  (93.5% reduction)
  words (approx. tokens)  493 -> 34  (93.1% reduction)

3. PDF read (a real 2 MB file)

An actual 2,097,152-byte PDF, read once as raw bytes, once through tsaver read --stats, which extracts the embedded text.

tsaver stats
  lines                   34 -> 34  (0.0% reduction)
  bytes                   2097152 -> 1805  (99.9% reduction)
  words (approx. tokens)  231 -> 231  (0.0% reduction)
The word count shows 0% reduction here — not a bug. There's no plain-text version of a binary PDF to count words in before extraction, so tsaver sets "raw words" equal to the already-extracted text's word count; the two numbers are always identical for PDFs. The byte number is where the real story is: a 2 MB file became 1.8 KB of text.

4. MCP-style JSON, array-shaped (real npm search response, 250 items)

A genuine 265,343-byte JSON response (npmjs.org's search API, fetched live), compacted with tsaver mcp --stats.

tsaver stats
  lines                   1 -> 326  (-32500.0% reduction)
  bytes                   265343 -> 8925  (96.6% reduction)
  words (approx. tokens)  1340 -> 579  (56.8% reduction)

This is the clean win case for tsaver mcp: the top-level array of 250 result objects gets truncated to its first/last few entries, and the byte/word savings are both real and large. (Lines go up because the output is pretty-printed for readability — that's expected and not a meaningful number here.)

5. MCP-style JSON, object-keyed (real npm registry response for express)

A genuine 823,555-byte JSON response — the full npm registry record for the express package, with 290 published versions — run through the same tsaver mcp --stats.

tsaver stats
  lines                   1 -> 41050  (-4104900.0% reduction)
  bytes                   823555 -> 1186118  (-44.0% reduction)
  words (approx. tokens)  11705 -> 80304  (-586.1% reduction)
This one got worse, and the report isn't hiding it. tsaver mcp's truncation logic only applies to JSON arrays. This payload's large collections (versions, time) are JSON objects keyed by version string, not arrays — so none of that data gets truncated, and it all survives in full. Combined with pretty-printing the output (2-space indent, for readability) instead of keeping the original's minified form, the result is larger on every axis than the input. If your MCP responses are large object-keyed maps rather than arrays, tsaver mcp in its current form will not help and can make things worse.

6. A real, already-small npm install

Installing three small packages (lodash, chalk, uuid) with warm npm/registry caches — a genuinely quiet install with no progress-bar or repeated-line noise to strip.

tsaver stats
  lines                   26 -> 26  (0.0% reduction)
  bytes                   1412 -> 1412  (0.0% reduction)
  words (approx. tokens)  172 -> 172  (0.0% reduction)

Zero reduction, and that's the honest result for this input — there was no noise to filter. tsaver's savings scale with how repetitive the original output is; a short, already-clean log has nothing to collapse.

What this actually tells you

  • tsaver run on anything with repetitive line noise (test suites, builds, verbose installs) is a reliable, large win — 85–94% reduction on both bytes and the token-count proxy in every real noisy-output case tested here.
  • tsaver read on PDFs/notebooks is a reliable, large byte win, but its "tokens saved" number is structurally meaningless for these file kinds — judge PDF/notebook reads by bytes, not words.
  • tsaver mcp only helps when the payload's bulk lives in JSON arrays. On this run's array-shaped payload it cut bytes by 96.6%; on the object-keyed payload it made things 44% worse. Check which shape your data is before assuming it will help.
  • Already-quiet output sees no benefit — tsaver has nothing to remove if there's no noise to begin with, and reports that honestly as 0%, not a fabricated number.

Methodology

How every number on this page was produced — so you can reproduce or challenge any of it.

  1. History was cleared with tsaver history clear --force immediately before this benchmark session, so nothing here is left over from unrelated usage.
  2. Scenarios 1–2 are real, executable shell scripts (not hand-typed example text) producing genuinely repetitive output, run once with plain shell redirection for the "without" baseline and once through tsaver run --stats for the "with" result — same script, same machine, back to back.
  3. Scenario 3 is a real 2 MB PDF already present in this project, read once as raw bytes (stat) and once through tsaver read --stats.
  4. Scenarios 4–5 are real JSON responses fetched live from the public npm registry at the time of writing (registry.npmjs.org's search endpoint and the express package record) — not synthetic or hand-constructed payloads — piped through tsaver mcp --stats.
  5. Scenario 6 is a real npm install of three small public packages, run with --loglevel info, node_modules removed beforehand so the install actually executes rather than no-op'ing.
  6. Every number quoted above is copied verbatim from the tsaver stats block each command printed to stderr, or from wc -c/wc -w on the independently-captured raw output. None are estimated, rounded for effect, or adjusted.

"Words (approx. tokens)" is a whitespace-split word count, the same proxy used throughout tsaver's own --stats output — documented everywhere as an approximation of token count, not an exact tokenizer measurement.
