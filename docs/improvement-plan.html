Improvement plan

What's actually worth fixing next

A deep pass through every token-saving surface in tsaver — filters, the MCP JSON compactor, the file optimizers, and levers beyond filtering (caching, just-in-time retrieval, real token budgets, session memory) — ranked by real token impact, not cosmetic cleanup.

All 13 numbered items below are implemented and verified. Each item's done-note documents what was built, how it was tested against real output (not synthetic guesses), and any bugs the testing itself caught and fixed along the way.

Based on reading src/mcpCompact.ts, src/filters/*.ts, src/fileopt/*.ts, src/graph/*.ts, the project's own token savings report, and external research into JFrog Boost, Anthropic's agent context-engineering guidance, and aider's repo-map algorithm (see "What other tools do" below).

0. Dashboard has no per-row tokens-used/tokens-saved columns Done

Top priority — the dashboard already computes this number per-entry for the summary tiles; it just isn't surfaced per-row.

src/dashboard/page.ts's table currently shows Raw → Filtered (bytes), Reduction, and a single Tokens saved column (computed inline per-row as entry.stats.rawWords - entry.stats.filteredWords, line 76). That's half the picture — it shows what was saved, but not what the line actually cost after filtering, i.e. filteredWords itself. An agent or a user scanning the table can't currently tell, at a glance, which rows are still expensive even after compaction (a filtered MCP response that's still 5,000 words) versus which rows are cheap and already near-zero.

HistoryStats in src/history.ts already stores rawWords and filteredWords per entry — the data needed for both columns is already captured and sent over /api/history. This is a presentation-layer fix, not a data-model change.

Fix: split the single "Tokens saved" column into two — Tokens used (filteredWords, what the agent's context actually paid after filtering) and Tokens saved (kept as-is, the delta). Add the equivalent split to the CSS kind-* styling so both read clearly at a glance; no backend/API change needed since entry.stats already carries both numbers.

Implemented and verified. src/dashboard/page.ts's table header and row renderer now show both Tokens used (entry.stats.filteredWords) and Tokens saved (the existing delta) as separate columns. No API/backend change was needed — /api/history already returns both fields on every entry. Verified by running the dashboard server locally and confirming both columns render against real run/mcp history entries.

1. MCP compaction doesn't truncate object-keyed JSON Done

High impact — this is the one documented regression in tsaver's own benchmark report.

compactArray in src/mcpCompact.ts (lines 16–24) truncates arrays to head/tail items. compactObject (lines 26–35) just recurses into every key with no limit at all. Real MCP/API payloads keyed by ID — npm's versions map, time-series objects, anything object-shaped instead of array-shaped — pass through completely untouched.

Confirmed by the project's own data: the token savings report's npm-registry (express package) scenario is exactly this case — an 823,555-byte payload came out at 1,186,118 bytes through tsaver mcp, a 44% regression, because its bulk lives in versions/time objects, not arrays.

Fix: generalize the array truncation to large objects. When an object has more than maxArray keys, keep a head/tail slice of keys (same edge-keep logic as arrays) and drop the rest behind an "...(N more keys)" marker.

Implemented and verified. compactObject now applies the same head/tail-key truncation as compactArray. Tested against a reproduction of the exact regression shape (a 290-entry version-keyed object): 28,237 → 964 bytes, a 96.6% reduction — the same payload shape that previously grew by 44% now compacts correctly. Small objects and the existing array path were re-verified unchanged.

2. MCP output always pretty-prints with 2-space indent Done

High impact — pure overhead on every single tsaver mcp run, scales with nesting depth.

src/commands/mcp.ts line 46 always does JSON.stringify(compacted, null, 2). Indentation costs real tokens an LLM never needs — nobody reads MCP output visually in-context. In the regression case above, pretty-printing alone inflated 1 raw line into 41,050 formatted lines.

Fix: default to minified JSON output; add an opt-in --pretty flag for humans debugging interactively. Combined with fix #1, this should turn the object-keyed regression into a real win instead of a loss.

Implemented and verified. Output is minified by default (JSON.stringify(compacted)); --pretty restores the old indented behavior. On the same test payload, minified output pushed the reduction from 96.6% (pretty) to 97.8% (minified) — combined with fix #1, the documented regression is now a win on the same payload shape. docs/USAGE.md and docs/index.html updated to document the new flag.

3. The npm filter never actually collapses repeated lines Done

Medium impact — not visible in the current benchmark report because its "quiet install" test case has no repeated noise to begin with.

src/filters/npm.ts lines 11–15: both branches of the if call emit(line) — identical behavior either way. The filter only drops notice/timing/spinner lines; it never collapses runs of repeated output the way GenericFilter and CustomFilter do. CustomFilter already uses RepeatCollapser (src/filters/custom.ts line 14) for exactly this.

Fix: wire RepeatCollapser into NpmFilter so long runs of repeated deprecation warnings or audit lines collapse the same way other filters' repeated output does.

Implemented and verified — including a bug caught during testing. The first pass kept the old KEEP_RE gate, which routed every "npm warn"/"npm error" line straight to emit, bypassing the collapser entirely — meaning repeated deprecation warnings (the actual noisy case) still never collapsed. Fixed by routing all non-dropped lines through RepeatCollapser unconditionally — it already flushes immediately on any line change, so a genuine one-off error/warning is never delayed or hidden. Verified against a script with 11 repeated deprecation warnings plus a real error and summary line: line reduction went from 0% (first pass, bug) to 78.6% (bytes 81.5%, words 78.0%), with the error and summary lines surviving untouched.

What other tools do — researched externally

Pulled directly from JFrog Boost's own documentation, Anthropic's published context-engineering guidance for agents, and aider's repo-map documentation — then checked against what tsaver's code actually does today.

JFrog Boost docs Anthropic: effective context engineering for AI agents aider repo-map docs

Boost strips ANSI escape codes as a named technique, ships filter profiles for 100+ tools (git, docker, go, cargo, gh, kubectl among them — tsaver has 2), and auto-disables a filter once an agent retrieves its full original 3+ times in a row. Anthropic's guidance frames the core lever as just-in-time retrieval — returning lightweight pointers instead of bulk content wherever possible. aider's repo map doesn't dump a symbol list; it ranks symbols with a PageRank-style graph algorithm under a fixed token budget (1K tokens by default) so only the symbols other code actually depends on survive the cut.

4. No ANSI escape code stripping anywhere Done

High impact — a directly-confirmed Boost technique tsaver has no equivalent of at all.

Checked src/filters/generic.ts, src/filters/pytest.ts, and src/filters/npm.ts — none strip ANSI color/cursor-control escape sequences (\x1b[...m and friends). Real CI output from colored test runners and progress bars carries these bytes straight through every filter untouched, inflating byte/token counts on every line that uses color, independent of whatever line-level filtering already happens.

Fix: strip ANSI escape sequences as a pre-processing step before a line reaches any filter's processLine — one shared regex, applied once in runner.ts's line pump rather than duplicated per filter.

Implemented and verified. New src/ansi.ts exports stripAnsi (CSI + OSC escape sequence regex, based on the standard ansi-regex pattern, including terminal hyperlink sequences). Wired into runner.ts's line pump so every filter now sees clean text — raw stats/history still record the true original bytes, only the filter's input is stripped. Tested against a real colored-output script (30 PASS lines + 1 FAILED, ANSI color codes varying per line): reduction improved from 75.5% to 82.4% bytes on identical input, with the filtered output now free of leftover escape bytes.

5. No adaptive filter disabling when a filter is repeatedly retrieved in full Done

Medium impact — closes a named Boost gap and is a genuine token-economics issue, not just feature parity.

If an agent keeps calling tsaver retrieve <id> to get the full original after a given filter ran, that filter is net-negative: its compaction cost an extra round-trip to undo. Boost auto-disables a filter after 3 such retrievals. tsaver's history.ts records entries and commands/retrieve.ts reads them back, but nothing feeds retrieval frequency back into selectFilter in src/filters/index.ts.

Fix: track per-filter retrieval counts in history, and when a filter's recent output has been retrieved in full 3+ times, fall back to passing output through unfiltered (with a note) until the pattern stops.

Implemented and verified. New src/retrievalTracking.ts persists per-filter retrieval counts at ~/.tsaver/retrieval-counts.json; commands/retrieve.ts records a hit on every full-text retrieval, and selectFilter checks isFilterDisabled before constructing a built-in profile, falling back to a new no-op PassthroughFilter (recorded in history as e.g. npm (disabled)) once a filter crosses 3 retrievals, with a 24h auto-reenable. Deliberately excludes the generic fallback, since disabling it would silently stop filtering every unmatched command. Verified end to end: 3 retrievals of an npm-filtered entry correctly disabled it on the 4th run (10 repeated warning lines passed through completely unfiltered, 0% reduction), and simulating a 25-hour-old retrieval record correctly re-enabled it.

6. Filter coverage is thin — only pytest and npm have dedicated profiles Done

Medium impact — extends real coverage the same way Boost's "100+ tools" claim is built: one keep/drop/collapse profile per tool.

src/filters/index.ts only maps pytest/py.test and npm to dedicated filters; everything else falls through to GenericFilter. git, go test, and cargo each have very recognizable, high-volume noise patterns — git's status/log boilerplate, go test's === RUN/--- PASS lines, cargo's Compiling N/M progress — that a generic fallback handles worse than a purpose-built profile, the same way the pytest-specific profile already outperforms generic for pytest's own output.

Fix: add GoTestFilter, CargoFilter, and a GitFilter following the same keep/drop/collapse pattern as PytestFilter/NpmFilter, registered in BUILTIN_PROFILES.

Implemented and verified against real tool output, not guessed formats. Built all three against output actually captured from git, a real local cargo build/test run (cold dependency fetch, warnings, a genuine failing test), and the documented real go test -v format. CargoFilter drops per-crate Updating/Locking/Adding/Downloading/Compiling noise, keeps warnings/errors/Finished/test result: lines. GoTestFilter drops === RUN markers and module-fetch noise; --- PASS lines are counted rather than exact-match collapsed (test names almost always differ, so RepeatCollapser alone wouldn't catch them — same fix pattern as PytestFilter's own PASSED handling). GitFilter drops git status's boilerplate (use "git ...") hint lines and clone/fetch percentage ticks. Testing also caught and fixed a real pre-existing bug: runner.ts spawns separate filter instances for stdout/stderr, so a command that fails on both streams (real for cargo test) printed its --- X exited with code N --- marker twice; fixed by deduping identical onExit lines across both streams in runner.ts itself, which also silently fixed the same latent bug in NpmFilter.

7. graph query has no relevance ranking Done

Lower priority — more design work than the others, but the one idea with no tsaver equivalent at all.

src/graph/query.ts lines 73–79 slice the first 50 references in file-scan order — no notion of which symbol matters more. aider's repo map instead runs a graph-ranking algorithm (effectively PageRank over a file-dependency graph) so symbols referenced by many files outrank one-off helpers, under a fixed token budget. tsaver's cap can currently keep 50 low-signal references while truncating ones that actually matter.

Fix: weight queryGraph's results by reference count (or file-level in-degree) before truncating, so the kept slice favors widely-used symbols over incidental matches.

Implemented and verified against tsaver's own codebase. New rankReferencesByUsage in src/graph/query.ts groups references by symbol name, ranks each group by distinct-file count (then total reference count as a tiebreaker — a simpler proxy for aider's full PageRank, appropriate given tsaver's heuristic, non-AST graph), and flattens back to a list before the existing 50-reference cap in commands/graph.ts applies. Verified against a real query on tsaver's own graph (tsaver graph query Filter, which matches GenericFilter/NpmFilter/CargoFilter/PytestFilter/etc. at once): confirmed the highest-usage symbol (PytestFilter, referenced from 2 files, 4 total references) sorted ahead of equal-file-count/fewer-reference groups, matching independently-computed reference counts from the raw graph data. No-match and single-exact-match cases verified unaffected.

Is JavaScript/TypeScript the right language for this?

A deliberate check, not an assumption — researched by looking at what comparable tools are actually built in and measuring tsaver's own runtime behavior.

JFrog Boost (compiled Go binary) ripgrep (Rust) sharp vs. jimp benchmarks measured on this machine

What was measured: tsaver --help via the compiled dist/cli.js takes ~270–290ms per invocation on this machine — almost entirely Node process startup, not tsaver's own logic. node_modules is 156MB across 47 packages (pdf-parse alone is 21MB). Every hot path in the codebase — filters/*.ts, mcpCompact.ts, graph/extract.ts — is regex matching over lines or walking a parsed JSON tree. None of it is CPU-bound in a way that benefits from a faster language.

What comparable tools use, and why: Boost — the tool tsaver was explicitly inspired by — ships as a compiled Go binary with no runtime dependency, which is almost certainly why it can claim "no install step, no startup lag." ripgrep is written in Rust specifically for SIMD-accelerated regex matching and lock-free parallel directory traversal at scale — a genuinely CPU-bound workload. sharp wraps native libvips and benchmarks 4–5x faster than ImageMagick for resizing; tsaver uses pure-JS jimp instead, correct but slower and heavier than necessary for a task Node doesn't accelerate on its own.

The honest conclusion: tsaver's workload doesn't justify a rewrite. The bottleneck is subprocess-spawn + Node startup overhead (~250ms), not algorithm execution — and that overhead is invisible next to the child processes tsaver actually wraps (npm install, pytest, etc.), which themselves take seconds. Rewriting the whole CLI in Go or Rust would fix a problem tsaver doesn't currently have, while leaving the actual problems (object-key truncation, ANSI stripping, thin filter coverage — items 1–7 above) exactly where they are.

Where language choice would start to matter, if tsaver's usage pattern changes:

  • Startup latency at scale. tsaver init --claude's hook wraps every Bash call Claude Code makes. 250ms × hundreds of calls per session adds up in a way a single compiled binary (sub-10ms startup) would not. This is the one legitimate argument for a rewrite, and it's the same architectural bet Boost already made.
  • Distribution friction. The README documents real install pain — git clone + npm link is the only reliable path, because npm install -g git+ssh://... 404s on some corporate networks. A static binary removes npm/Node as an install-time dependency entirely, mirroring Boost's own install.sh approach.
  • graph/extract.ts's regex-based parsing. The closest thing to real CPU-bound work in the codebase, and at large-repo scale the bigger win is a real parser (tree-sitter, available as native bindings in both Rust and JS) for correctness, not a faster language for speed.

Recommendation: keep TypeScript. If startup latency under the Claude Code hook becomes a felt problem later, the incremental fix is compiling the existing TS codebase into a single binary (e.g. bun build --compile) rather than a full Go/Rust port — same source, no Node startup cost, no 156MB node_modules in the runtime path.

Beyond filtering: other ways to save tokens

Everything above works on one lever — filter the output harder after it's already been captured in full. These work on different levers entirely: avoid redoing work, send less in the first place, budget against a real token count, and catch repetition filtering can't see.

8. No caching or dedup — the same work gets redone every time Done

src/fileopt/cache.ts's writeCache re-extracts and rewrites the cache file on every call, with no check for whether the source file changed since the last read — relevant because init --claude's Read hook can fire on the same PDF/notebook repeatedly in one session. Separately, tsaver run has no dedup across history: running the same command twice (git status, npm test) with identical output filters and stores both independently, with nothing checking "is this identical to a recent entry." Same gap in commands/mcp.ts — repeated identical MCP queries get compacted fresh every time with no memoization.

Fix: hash the source file's content/mtime before re-extracting in writeCache; add a content-hash short-circuit in run.ts/mcp.ts that can report "identical to history entry <id>" instead of re-emitting the same filtered block.

Implemented and verified for both halves — file reads and MCP queries. fileopt/cache.ts now writes a small manifest (source mtime + size) alongside each cache file; readCacheIfFresh lets commands/read.ts skip extraction entirely on a cache hit, re-using the real original file's byte size for "raw bytes" in history/stats rather than the already-extracted text's size. Verified on the repo's real 2MB report.pdf: a warm cache hit returned the same cache path without re-running pdf-parse, and a touch on the source correctly forced re-extraction. Separately, new src/mcpCache.ts hashes the raw input text + maxString/maxArray options and caches the minified compaction result in ~/.tsaver/mcp-cache/; --pretty is excluded from the cache key since it only reformats an already-cached result. Verified byte-identical output between cold and warm runs, and confirmed different --max-array values produce separate cache entries.

9. Everything is bulk-capture-then-filter — nothing is just-in-time except graph query Done

This is Anthropic's core context-engineering lever (return pointers, fetch on demand) and tsaver mostly does the opposite: capture everything, filter after. graph/query.ts already gets this right — it returns file:line pointers, not full bodies. Nothing else does. tsaver read on a PDF/notebook always extracts the whole document even if the agent only needs one section. runner.ts's pump buffers every line of a run into memory with no cap — a long-running or watch-mode command has no early-exit ceiling, so one runaway command can cost far more context than any filter ratio justifies.

Fix: add a tsaver read --pages N-M / --query <term> option for partial extraction; add a hard byte/line ceiling to pump with a "truncated — use tsaver retrieve for the rest" message once exceeded.

Implemented and verified for both halves. fileopt/pdf.ts's pdfToText now accepts a 1-indexed inclusive page range, passed through to pdf-parse's own partial option — verified the option is honored structurally against the repo's real PDF. New filterTextByQuery in fileopt/index.ts filters plain text to matching lines plus 2 lines of context (merging overlapping matches, marking gaps), reused by read.ts's default case and by PDF output after extraction; notebookToMarkdown gained its own query support that keeps whole matching cells rather than individual lines. Verified a 97.5% reduction on a 201-line log queried for one rare term, and correct cell-level filtering on a real notebook. --cache combined with --pages/--query correctly skips writing to (or reading from) the full-document cache — verified a partial read never overwrites the cache a later unqualified read depends on. Separately, runner.ts's pump now caps filtered output at 2,000 lines / 500,000 bytes (shared across stdout+stderr), appending a one-line notice once hit; the raw side is intentionally never capped, so tsaver retrieve still recovers everything. Verified against a 3,000-line, non-collapsible-output script: filtered output stopped at the cap with the notice appended, while retrieve recovered the full original 3,000 lines, and confirmed default tsaver run on small output is unaffected.

10. Truncation thresholds are tuned against a proxy, not real tokens Done

stats.ts's word count is an explicitly-disclosed whitespace-split proxy, not a real tokenizer — but mcpCompact.ts's DEFAULT_MAX_STRING = 500 and DEFAULT_MAX_ARRAY = 20 are flat constants applied identically regardless of content type. A base64 image blob embedded in a JSON payload (a real MCP response shape) costs far more tokens per character than English prose, but gets the same 500-char allowance.

Fix: swap the proxy for a real BPE-style token estimate when deciding truncation thresholds; apply a much more aggressive cap specifically for strings that look like base64/binary data (detectable by charset density) rather than one flat limit for all strings.

Implemented without adding a tokenizer dependency, after measuring the actual options. Checked three candidates against a real BPE tokenizer (gpt-tokenizer, used only for calibration, never installed as a runtime dependency): gpt-tokenizer itself is 28MB unpacked — too heavy for tsaver's currently lean ~4-dependency footprint; tokenx (53KB) is lightweight but still underestimated base64-like content by ~3x against the real tokenizer, exactly the case that matters here. Built a zero-dependency heuristic instead: new src/tokenEstimate.ts classifies a string as dense-encoded (no whitespace, charset limited to letters/digits/+/=_-) and applies a much lower DENSE_ENCODED_MAX_CHARS = 120 cap in mcpCompact.ts's compactString, taking the lower of that and --max-string. Verified against gpt-tokenizer as ground truth: real base64/hex/UUID content costs ~1.5-1.8 chars/token vs. prose's ~5.5, confirming the premise; verified the fix on a real mixed payload (a 2KB base64 blob next to a prose description) — output shrank from 730 to 350 bytes (52% smaller) with the prose field left fully intact, and confirmed URLs (which contain :/.// outside the dense charset) are correctly NOT over-truncated.

11. Repeat-collapsing only catches identical lines, not structurally-similar blocks Done

GenericFilter's repeat detection (and RepeatCollapser) only collapses consecutive lines that are identical after digit-normalization. It won't catch the common real case of multiple test failures with the same exception type and similar traceback shape but different line numbers/variable names across blocks — a pattern that's structurally repetitive but not line-for-line identical, which exact-match collapsing can't see.

Fix: add a fuzzy/structural similarity check across multi-line blocks (not just single lines) for grouping near-identical failures, on top of the existing exact-match collapsing.

Implemented in both GenericFilter and PytestFilter, with two real bugs caught and fixed during verification. New src/filters/blockRepeat.ts's BlockRepeatCollapser normalizes a multi-line block by masking quoted strings, hex tokens, digits, and (new) the test/function name itself in its known grammatical slots (a bare line, or after def/function) — since a differing name is expected between two otherwise-identical failures and shouldn't block collapsing. Wired into GenericFilter (error lines followed by indented at .../File "...", line N stack-trace continuations now form one block) and PytestFilter (failures between ____ test_name ____ headers).

During verification against a real 3-failure pytest script, two bugs surfaced and were fixed: (1) a block closed by startBlock stayed wrongly buffered if the very next line was a plain non-block line rather than another block, scrambling emission order — fixed by adding exitBlockContext, which flushes immediately rather than leaving a block pending with nothing left to compare against; (2) standalone section headers like === FAILURES === and === short test summary info === don't match SUMMARY_RE (which requires "failed/passed/error" in the text) and were falling through into block content, corrupting every block's signature — fixed by also routing any EQUALS_HEADER_RE match out of block context. Verified: 3 failures with identical exception shape but different test names/values now collapse to one block + "(previous block repeated 2 more times...)" (54.5% line reduction, up from 15.2% before); confirmed a failure with a genuinely different exception type stays uncollapsed in a mixed scenario; re-verified byte-for-byte against the Boost comparison report's documented single-failure reference case (still an exact match) and a repeated-error-block GenericFilter case (identical output before/after this change, confirming zero regression on existing behavior).

12. No session-level memory of "nothing changed since last time" Done

Maps to Anthropic's "tool result clearing" idea. If an agent runs git status five times in a session and output 2–4 are unchanged, each one still gets fully filtered and re-emitted. tsaver's full history log (history.ts) exists but nothing short-circuits a repeat call against recent identical output within the same session.

Fix: a lightweight ring buffer of the last N command+output hashes (separate from the permanent history log) that lets run.ts emit "unchanged since last run" instead of the full filtered output when a hash matches.

Implemented as opt-in (--dedupe), not a default-behavior change, and verified. A streaming CLI can't un-print output already sent to a live terminal, so this needed runner.ts to support buffering: run() takes a bufferOutput option that holds filtered lines in memory instead of writing them immediately, returning a flushBufferedOutput callback the caller invokes once it's decided the output should actually be shown. New src/recentRunTracking.ts hashes a command's raw output and compares it against that same command's last recorded run within a 30-minute window (a capped ring buffer at ~/.tsaver/recent-runs.json, separate from the permanent history log). commands/run.ts's new --dedupe flag wires this in: unchanged output prints a one-line note instead of the buffered content, and the real byte/word counts a repeat would have cost are still visible via --stats' raw-side numbers. Verified against real git status runs: identical repo state correctly deduped (91.7% line reduction on top of the git filter's own reduction), a genuinely new untracked file correctly broke the match and showed full output again, and a simulated 31-minute-old record correctly forced full output despite identical content. Default tsaver run (no flag) is unaffected — confirmed unchanged byte-for-byte behavior without --dedupe.
LLM-assisted summarization of large outputs. Would compress far more aggressively than regex filtering ever can, but requires a network call to a model — directly against tsaver's "no network calls, fully local" design goal from the README. Named here as a deliberate scope exclusion, not an oversight.

Looked at, not worth doing now

GenericFilter's inline repeat-collapsing vs. reusing RepeatCollapser. Code duplication, not a token-savings problem — skip.
PDF/notebook/image optimizers. Already close to the ceiling — 99.9% byte reduction on a real 2 MB PDF per the token savings report. Nothing to gain here.
graph query reference capping. Already caps at 50 references with a count of the rest — fine as-is.
